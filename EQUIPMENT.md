# Character equipment reference

Equipment is a manually maintained website profile. It never changes game inventory, auction results, DKP, attendance, or ownership. Nothing is automatically equipped after an award. Selecting the same item in multiple slots is allowed because the catalog can be incomplete and this is a reference profile.

Authenticated members may read `GET /api/characters/:id/equipment`. The response contains `character` (`id`, `name`, `className`, `kind`, `ownerId`), `canEdit`, and 23 ordered `slots`. Each slot contains `key`, `label`, `sourceSlot`, `itemId`, `itemName`, `source`, and `updatedAt`. Empty slots have null item, name, source and initially null time. Cleared slots retain their last update time. The canonical keys are charm, ear1, head, face, ear2, neck, shoulders, arms, back, wrist1, wrist2, ranged, hands, primary, secondary, finger1, finger2, chest, legs, feet, waist, powerSource, ammo. Source slot labels are uppercase EQ names; ranged uses RANGE and powerSource uses POWER SOURCE.

`PUT /api/characters/:id/equipment/:slot` accepts JSON `{itemId, expectedItemId}`. Both fields are required, and each is null or a positive safe integer. Only the current approved main/alt owner may edit, including when the caller is an administrator or officer. Other members' profiles are read-only. The current profile also requires write access to Overview or Mains and attendance. Requests require the session CSRF token and exact same Origin. Current ownership and expected selection are checked again in the atomic mutation, while the bundled access guard rechecks the required permission. Character detachment retains saved equipment but immediately removes the former owner's edit permission. Only cached item references may be selected. Partial class or slot metadata does not impose restrictions; the UI can provide guidance.

Successful writes return `{slot, alreadyApplied:false}`. Retrying a selection already present returns `alreadyApplied:true` without another audit row. A conflicting current selection returns 409 `equipment_conflict`; clients should reload the profile. Comparison uses the item value rather than a version, so item-value ABA is deliberately permitted. No ownership epoch is accepted by this endpoint. Invalid slots return 400 `invalid_slot`, missing catalog entries 400 `unknown_item`, and editing another member's character 403 `forbidden`.

The saved `source` is `award` only when a confirmed award exists for that exact character and item at selection time; otherwise it is `reference`. Pending awards and awards belonging to another character do not qualify. This label records provenance at the time of selection and does not refresh automatically. Equipment responses and audits contain no sealed bids or bid prices.

Apply `worker/equipment.sql` through the normal additive migration path. Equipment selections and before/after audit records commit together. Clear operations retain a nullable row for history timing; the immutable audit records describe each actual set/clear. Equipment never reverses a charge, transfers historical awards, or grants attendance credit. Focused verification: `node --test tests/equipment.test.mjs` uses disposable in-memory SQLite only.

The bundled worker uses `createEquipmentApi({knownItems: VERIFIED_ITEM_REFERENCES})` so verified starter items already visible in catalog searches can be selected on a fresh database. A missing starter reference is inserted from those server-supplied facts in the same transaction as the authorized, optimistic equipment change and audit. Reads do not seed the database; arbitrary uncached client IDs remain rejected. Failed ownership guards and rolled-back audits leave no new reference behind. The standalone `handleEquipmentApi` export uses no starter facts by default.

When an access context is present, `canEdit` and mutation preflight require level3 for Overview or Mains and attendance. A missing, null or read-only permission map cannot use an administrator role to override that restriction. The standalone handler without an access context retains owner-only compatibility for bounded module tests; production requests pass through the bundled access middleware. Audit details snapshot `subjectUserId` as the actual owner performing each gear change.
